5. Configure the policy¶

This step creates policies/unitree/policy.yaml. For the full field reference, see Policy options — this page derives every value for the unitree_rl_mjlab G1 velocity policy and gives you the complete file.

Create the folder¶

mkdir -p policies/unitree

The policy will be named after this folder (unitree), matching the default_policy: unitree already set in Configure the controller.

Finding the information¶

We are going to check their velocity policy folder for G1 : deploy/robots/g1/config/policy/velocity/v0 

deploy/robots/g1/config/policy/velocity/v0/
├── exported/
│   └── policy.onnx
└── params/
    └── deploy.yaml

params/deploy.yaml is what this step actually translates — it's the exact deployment spec the policy was exported with: per-joint stiffness/damping, default pose andaction scaling. It also has the observation list in training order, that we need for Observation configuration.

Field-by-field mapping¶

deploy.yaml policy.yaml Notes
stiffness control.kp Direct copy, per joint name.
damping control.kd Direct copy, per joint name.
default_joint_pos action.q0 This is the pose q_rl uses at every policy update, adding to it the scaled action — see Architecture: default pose.
actions.JointPositionAction.scale action.scale Per-joint action scale.
step_dt control.period_s The policy's inference period.
commands.base_velocity.ranges control.vel_cmd_speed Not a direct copy — see below.
(observation gait_phase.params.period) control.phase_period 0.6, from the gait_phase observation's params in the same file — used again in the next step.

action.joints: all and control.use_QP: true come from the convention and from wanting the CBF-QP safety layer enabled, not from deploy.yaml.

vel_cmd_speed is a judgment call¶

commands.base_velocity.ranges describes the training distribution: lin_vel_x is asymmetric (-0.5 to 1.0), lin_vel_y and ang_vel_z are symmetric. control.vel_cmd_speed in policy.yaml, by contrast, sets the symmetric maximum magnitude the GUI/joystick command widget will ever send (see Available observations: command). There's no single correct way to collapse an asymmetric training range into a symmetric runtime limit — this integration picked:

  • xy: 0.5 — the lateral bound and the backward bound of the trained range, applied uniformly; conservative on the forward side (which trained up to 1.0) in exchange for a simple, symmetric joystick mapping.
  • yaw: 1.0 — the trained range is already symmetric, so no compromise needed.

Revisit this if you want to command higher forward speeds and are comfortable operating closer to the edge of the trained distribution.
